# Due Good master implementation plan

## Outcome

Build a small, public, responsive student assignment tracker for Marymount Canvas that begins with one safe, consented course import and expands only after its persistence, sync, and student-state guarantees are proven. This is one four-phase plan. Each phase ends in a local commit; the commits are pushed once, after phase 4 and the complete pre-push suite pass.

## Current baseline

- The repository contains a specification handoff, synthetic fixtures, a legacy UI reference, and offline validation utilities. It has no application runtime, cloud resource, OAuth credential, or live Canvas proof.
- The supplied design-reference PNGs are local-only creative input. They are not source assets, test baselines, or public repository content. Do not commit them without a separate publication decision.
- Current provider research is captured here because the supplied handoff is not implementation evidence:
  - Canvas developer-key, OAuth, pagination, and assignment facts use the canonical C1-C7 registry entries in `docs/SOURCES.md`; Task 1.1 rechecks them before implementation. If that source is unavailable, it records the gap and blocks only the dependent integration choice rather than silently relying on stale guidance.
  - Worker/D1 limits, enforcement, static-asset, and local-test integration facts use the canonical F1-F9 registry entries in `docs/SOURCES.md`; Task 1.1 rechecks current official documentation before dependency selection. An unavailable source produces a documented compatibility gap and no dependency selection or installation for that affected path.
  - The accessibility target uses the canonical A1 WCAG 2.2 registry entry; automation and keyboard/screen-reader review are evidence classes, not a visual-similarity claim.

## Scope and exclusions

Included: a TypeScript Worker with static assets and D1 candidate architecture; server-held credentials; student-scoped reads and writes; a complete, non-destructive Canvas import; student-owned planning; responsive light/dark interface; local, mocked, and browser tests.

Excluded until separately authorized: Cloudflare account changes, database creation, deployments, domains, paid services, Marymount developer-key submission or use, real OAuth credentials, production Canvas calls, a public pilot, course-wide/gradebook data, Canvas writes, LLM features, notification services, and multi-institution discovery.

## Delivery and quality rules

1. Establish the Node/TypeScript toolchain and committed lockfile in phase 1. Use Git-native `.githooks/` rather than a hidden machine-only hook configuration. The bootstrap task sets `core.hooksPath` through an explicit `npm run hooks:install` command and verifies it.
2. Every normal commit runs `npm run lint` and `npm run deadcode` through `.githooks/pre-commit`. Neither hook is bypassed.
3. `.githooks/pre-push` runs `npm run test:all`, which includes type checking, linting, dead-code analysis, Worker unit/integration tests, the single full browser batch, package checks, and an asset/secret scan. A phase gate first runs its focused non-browser checks, then runs `test:all` once; it does not run a second browser batch. Before *every* local commit, the captain also runs a staged-diff/public-history scan and secret scan; this is a mandatory commit procedure, not an extra slow pre-commit hook. GitHub secret-scanning push protection remains an independent final guard. No push occurs until phase 4 is accepted and this exact command passes.
4. Make cohesive local task commits plus a phase-boundary commit on `main`; retain all commits locally until the final push. Task 1.1 starts from the recorded main base plus this accepted plan snapshot, promotes the corrected public plan/source files in its first checked commit, and installs/verifies the fast hooks plus minimum staged public-tree/secret and baseline-integrity guards before that commit. At the start of each later task, `integrity:check` must pass against the preceding committed baseline. After expected edits, `integrity:diff` renders the checksum-path delta without writing; the captain compares it with the declared changed-file list, then performs a stated explicit regeneration and runs `integrity:check` again. Redacted command receipts live under gitignored `.evidence/`; the post-push receipt is local delivery evidence, not a pre-push status prerequisite. An unexpected start-of-task failure or an unreviewed delta blocks the commit. Do not amend or rewrite history in normal work. If a staged/history scan or push protection detects a secret or private record, stop, do not push or bypass it, rotate any exposed secret, and obtain owner direction for a clean local-history repair.
5. No remote operation, sync, browser run, or long command may be silent. The application reports user-visible progress without logging credentials, callback query strings, student data, or complete Canvas responses.

## Design direction derived from the supplied references

### Identity and theme

- Use a scholarly, restrained navy-and-gold identity. The reference palette anchors are Scholar Navy `#0E2A47`, Classic Gold `#B08D57`, Sage `#6A7F56`, Warm Stone `#F4F1E9`, Charcoal `#1F2937`, and Alert Red `#D64545`.
- Define semantic CSS tokens, not page-specific hex values: canvas, surface, elevated surface, text, muted text, border, focus, primary action, success, warning, danger, information, and course accents. Light and dark themes must use the same semantic names.
- Use Playfair Display only for brand/display headings and Inter for controls, metadata, and body text. The implementation must use a privacy-conscious, licensed font delivery strategy selected and verified when font assets enter scope; no unreviewed third-party font request is part of the first deployment.
- Treat the supplied DG monogram and quoted copy as visual inspiration only. Create no claim of Marymount endorsement, reuse of university marks, or copied quotation without an explicit asset/content decision.

### Information architecture

- Desktop uses a persistent side navigation, a compact top utility bar, and a responsive content workspace. The contextual rail is optional and collapses before primary content does.
- Mobile uses a compact header and five-item bottom navigation: Today, Timeline, Attention, Courses, and More. It contains only routes that are implemented and available to the current student.
- The initial usable slice is a minimal This Week route, course selection, assignment list, assignment detail, and connection/sync recovery. Timeline, Needs Attention, Courses, Completed, search, personal greeting, quick actions, and personalization are full phase-4 screens unless needed as an accessible route to phase-1 work.
- Assignment detail keeps Overview, Steps, Notes, and History distinct. Canvas submission is a source fact; personal completion and steps are student-owned planning. Their controls, labels, filters, and announcements never imply one another.

### Component and accessibility constraints

- Provide design tokens, an accessible button/input/dialog/list primitive set, course identity chip, assignment row, status badge, segmented/tab control, empty state, loading state, and error/recovery panel. Do not build a generic component platform.
- Status always has text and an icon or other non-color cue. Due, overdue, partial import, stale data, disconnected Canvas, quota exhaustion, and retrying sync have truthful distinct copy and programmatic status announcements where the state changes.
- Keyboard order follows visual order; focus is visible and unobscured; target size, contrast, reflow, reduced motion, headings, labels, and status messages are tested at the component and browser levels.
- Desktop and mobile screenshots test layout regression against repository-owned synthetic fixtures. The supplied PNGs are not golden images. The supplied reference files are committed to neither the tree nor its history; their explicit local ignore entries land with this planning checkpoint.

## Phase 1 — OAuth and Cloudflare foundation

### Goal

Create a secure local Worker/D1 vertical slice using synthetic Canvas responses. Authentication stays disabled unless every required configuration value is present; it never becomes a token-paste fallback.

### Work

1. Bootstrap the reproducible plain-TypeScript Worker/static-assets shell, pinned build tool, client-side router, Wrangler, local Worker/D1 testing, Playwright, an explicit test-path membership manifest, checked-in lockfile, Git-native hooks, and the minimum staged public-tree/secret plus baseline-integrity controls required before the first commit. Do not add a frontend framework, inline runtime script, or dynamic code path. Start from the recorded main base and this accepted plan snapshot; the first checked commit promotes the corrected public plan/source files and ignores local review prompts. Verify the current official Worker test integration and compatible pinned package set before installation, record those sources in `docs/SOURCES.md`, and document an unavailable-source or incompatibility finding instead of silently substituting a package. Define and verify a Python 3.10-or-newer preflight for the existing fixture tools used by the full suite. Build static UI source only into a dedicated asset directory configured in Wrangler; prove server modules cannot enter that browser bundle and no repository root directory is served. Establish one TLS-capable browser origin that accepts the declared secure cookie and supports service-worker registration for every later browser suite. Define one migration discovery/application contract for local D1, Worker tests, and local development; each migration-owning task proves its named migration is applied before schema-dependent behavior. The first commit is permitted only after the hook verifier, staged public-tree/secret scan, and baseline-integrity check succeed; Task 1.2 completes the richer status-record, receipt-store, and checksum-diff workflow before auth or import work.
2. Implement the minimum student/account/session/connection schema with an institution-scoped identity key from day one, server-only configuration boundary, an authenticated encryption key ring with an active version plus retained historical versions, and account/connection/format associated data. A key can be retired only after a verified zero-reference migration or an explicit connection deletion; lazy re-encryption preserves old-key decryptability until that condition. Use an exact redirect/origin allowlist and one-time browser-bound OAuth state. The Canvas OAuth profile defaults to the documented confidential authorization-code exchange: a registered client secret, exact redirect URI, state validation, and code exchange stay server-side. The profile may send PKCE only when the specific institution documents and approves it; an unverified PKCE claim never blocks the confidential profile, and any missing institution/client/redirect/scope proof keeps authentication disabled. Use hashed opaque sessions with explicit `__Host-` cookie attributes, absolute and idle expiry, server-side invalidation on logout/disconnect, and rotation at an authentication boundary; protect every registered state-changing route with session-bound CSRF validation. Test header construction locally and test browser acceptance only on the shared TLS-capable test origin; never weaken a secure cookie for HTTP local development. Add a short-lived, privacy-preserving auth-start throttle keyed by institution and an edge-derived client digest held only in isolate-local memory: it stores no raw client address and performs no D1 write. Only after authentication, apply per-account/per-connection controls. Add logout, disconnect, a deletion fence, and an owner-scoped query layer. The controls are not claimed as strict global distributed limits: they fail closed at locally observed thresholds and document bounded concurrent-attempt overshoot. Set restrictive response headers, including a CSP that supports the static application without unsafe inline content, no-store/no-referrer for callback responses, frame protection, and MIME sniffing prevention. Prove cross-student access is rejected. Disconnect attempts the validated configured provider revocation while the credential is present, then destroys it and blocks refresh; it retains an authenticated student's planner locally. The owner must confirm that proposed product policy before any public pilot.
3. Implement a typed Canvas adapter with synthetic responses only: course discovery, selected-course assignment import with student-specific date overrides, safe external-ID handling, validated pagination, staging, completeness checks, comparison, and commit. The same task owns the minimal student-scoped assignment-completion record and mutation route used by the phase-1 interface; it remains distinct from Canvas submission state and from phase-3 notes, overrides, subtasks, exceptions, rules, and review workflow. Before completing the import implementation or allowing Phase 2 to depend on it, run the synthetic small/typical/large import-envelope feasibility checkpoint and select the bounded in-memory or durable-staging strategy only if it completes within the documented local operation contract; failure stops that strategy at the Phase 1 boundary. Record client-orchestrated multi-request import as considered but deferred because a lost browser cannot guarantee completion; Phase 2's server-owned continuation is the first durable alternative. The incoming request has a configuration-derived operation budget below the documented free Worker CPU/subrequest and D1-query ceilings; local tests enforce operation counts and payload/row bounds but cannot prove deployed CPU. Before any public pilot, a reviewed synthetic staging run must demonstrate the actual Worker CPU and subrequest envelope; failure leaves onboarding disabled rather than adding a paid service. First request or validate a provider-supported string ID representation; if an unsafe numeric ID arrives, fail that resource closed, preserve its prior snapshot, and mark nothing unavailable rather than inventing a custom parser in phase 1. A complete snapshot becomes visible only by an atomic active-snapshot pointer swap. Staging may use bounded batches, but no batch can make an import visible: only the final O(1) pointer swap commits a complete snapshot. Phase-1 staging and final commit complete inside one bounded incoming Worker request, though that request may issue multiple bounded outbound Canvas fetches; no durable continuation exists before phase 2. Persist field presence and submission state as explicit supplied, null, unknown, or unsupported variants rather than inferring a non-submission. Phase 1 enforces configuration-derived request/page/query/row bounds, one resource lease with bounded expiry and safe next-attempt reclaim, and a generation fence; it fails closed before an import needs an unsupported continuation. Anomalous/empty inventory follows a complete-versus-filtered/recheck guard before anything is marked unavailable. A malformed, partial, over-budget, unauthorized, or interrupted import preserves the last committed view and announces partial state.
4. Add the limited responsive visual foundation needed to understand connection, sync, course selection, assignment list/detail, personal completion, Canvas submission including unknown/unsupported state, and every recovery state. The personal-completion control must round-trip through the phase-1 student-scoped mutation route and report failure honestly. Render imported content as text only; do not accept rich Canvas HTML. It uses the design direction above but defers nonessential feature screens and decorative polish.

### Phase gate and commit

- Gate: local Worker/D1 integration tests cover OAuth/CSRF/throttle rejection without pre-auth D1 writes, documented confidential-profile requirements plus any explicitly enabled PKCE profile, session expiry/invalidation/rotation and cookie attributes, every registered mutation route, ownership boundaries including identical provider IDs at distinct institutions, disabled-auth behavior, legacy-key decryption and lazy re-encryption, revocation ordering, exact outbound origin checks, restrictive headers, shared TLS/service-worker test-origin compatibility, named migration application, the import-envelope feasibility checkpoint, configured import ceilings, lease expiry/reclaim and generation fencing, complete-vs-partial import behavior, safe-ID fail-closed behavior, staged-batch/invisible-pointer behavior, per-student date overrides, unknown/unsupported submission states, and end-to-end personal-completion persistence separate from Canvas submission. Run the phase's focused non-browser checks, then `npm run test:all` once, staged public-history and secret scans, and integrity check before the boundary commit. These are not a claim of deployed CPU, live D1 semantics, or human screen-reader verification.
- Commit: `Phase 1: safe Canvas foundation`.
- Evidence boundary: mocked and local Worker/D1/browser checks only. Cloudflare deployment and Marymount OAuth remain unverified.

## Phase 2 — Sync durability and budget controls

### Goal

Make refresh bounded, idempotent, resumable, and honest under free-tier limits without promising background synchronization.

### Work

1. Add source snapshots, stable projections, change history, resource-level freshness, resumable continuations, bounded retries, durable lease/generation fencing, lazy safe re-encryption of a credential only after a successful authenticated connection use, and opportunistic expiry cleanup for abandoned staging/checkpoint rows. No fleet key-rotation sweep is claimed. A stored credential retains the version it was encrypted with until it is safely read through the key ring and re-encrypted under the active version; removing an old key before zero references exist is prohibited. Maintenance cleanup may delete only expired, uncommitted rows by a server-side predicate, returns no other student's data, and is independently tested for tenant opacity. An old job cannot overwrite a newer commit. The request that owns an admitted sync receives its bounded terminal progress/result. A duplicate tab receives an explicit in-progress lease response and may make one documented, bounded back-off status read after cooldown; it cannot start another refresh or rely on open-ended polling.
2. Add per-profile synthetic workload reports and documented-ceiling request/row/storage accounting, including every D1 read/write caused by post-auth throttling, admission, leases, and other control rows; pre-auth isolate-local memory throttling has no D1 cost. Add bounded retention for snapshots and history, a small conservative pilot soft-admission control, no-op minimization, on-open/manual refresh cooldowns, and explicit new-auth and sync kill switches. The switches are Worker configuration evaluated before D1 access, so an operator can stop new admission even when D1 is unavailable. D1-backed admission is explicitly approximate rather than a strict global counter: document its race-window overshoot bound, fail closed at a locally observed capacity threshold, and use the switches to stop new admission. A D1 limit/error makes all D1-derived reads and writes explicitly unavailable; it never claims a safe server-side read or serves another account's cached state. The UI may retain only its already-rendered in-memory screen with an unavailable label. Reconcile assumptions with the existing estimator. Local tests validate only arithmetic, conservative admission behavior, and failure handling; they do not measure Cloudflare CPU, deployed D1 semantics, or certify account capacity. Do not add cron, queues, or paid services.
3. Test duplicate work prevention, cancellation and disconnect races, refresh-token omission preservation, pagination failure, quota exhaustion, connection loss, and concurrent personal actions during a refresh. The actual account-deletion race is tested with the deletion implementation in phase 4.

### Phase gate and commit

- Gate: deterministic local concurrency and failure tests demonstrate that an incomplete import never deletes tasks or reports a full refresh, that abandoned staging is bounded and cleaned opportunistically, that an unavailable D1 binding denies D1-derived data rather than claiming safe reads, and that the pre-D1 operator switch stops admission. Run the phase's focused non-browser checks, then `npm run test:all` once, staged public-history and secret scans, and integrity check before the boundary commit. A reviewed synthetic staging measurement remains a public-pilot gate for Worker CPU, subrequests, and deployed D1 behavior.
- Commit: `Phase 2: durable bounded sync`.
- Evidence boundary: local measured scenarios only; account-level Cloudflare quota and live Canvas behavior remain unverified.

## Phase 3 — Generalization and student planning

### Goal

Remove personal-course assumptions while preserving the distinction between imported facts, student planning, and unaccepted suggestions.

### Work

1. Generalize identifiers, institutions, courses, terms, deadline representations, source aliases, time zones, and unknown/omitted fields with a forward-compatible additive migration. The phase-1 institution-scoped key remains stable. Task 3.1 begins by proving the intended additive change against the actual phase-1 schema preserves identity and provenance; failure stops before any schema mutation and requires a separately evidenced and reviewed rebuild proposal. Do not add a table-rebuild/migration-runner subsystem before that concrete need is established.
2. Extend the phase-1 personal-completion record with personal tasks, notes, display-title overrides, target work dates, subtasks, dismissals/exceptions, undo, reviewable changes, operation IDs, expected versions, and mutation receipts. Apply those operation-ID/expected-version semantics to every student-owned mutation, including the Phase 1 completion route, before Phase 4 offline replay may use it. Canvas refreshes cannot overwrite these fields; replayed or stale personal mutations cannot duplicate or overwrite them. Every new or upgraded state-changing route is registered and covered for authentication, CSRF, Origin/Referer, ownership, replay, and failure behavior in the task that creates it.
3. Support safe term rollover without hiding an ended-term course that has outstanding work. Preserve student-authored subtasks and exceptions without a generic rule engine, generated checkpoints, parent-progress calculation, or point accounting. Do not parse arbitrary syllabus prose into mandatory work; any future automation needs separate owner-approved product requirements and evidence.
4. Expand the local/browser suite with different course loads, date zones, submission states, personal exceptions, source removals, and two-user isolation cases. Account-isolated offline pending writes remain a phase-4 feature.

### Phase gate and commit

- Gate: tests prove that a deadline/source update preserves student notes and that conflicting facts/plans produce a review state rather than destructive merge. Run the phase's focused non-browser checks, then `npm run test:all` once for its only browser-inclusive batch, staged public-history and secret scans, and integrity check before the boundary commit.
- Commit: `Phase 3: generalized student planning`.
- Evidence boundary: synthetic multi-course data only; no claim of multi-institution or live Canvas support.

## Phase 4 — UI, accessibility, and offline experience

### Goal

Apply the complete design direction to the proven data and sync behaviors, then validate every screen and state on desktop and mobile.

### Work

1. Complete light/dark theme tokens, the restrained typography and course/status system, responsive shell, search, settings, and accessibility primitives. Pin the browser/rendering environment and a reviewed self-hosted-or-system font strategy before committing visual baselines. Preserve the phase-1 state vocabulary and never turn stale/partial data into reassuring but false copy.
2. Implement Timeline, Needs Attention, Courses, Completed, daily/weekly views, assignment detail tabs, guided personal steps, quick actions, and status/history affordances from the reference direction.
3. Implement a versioned static app-shell and offline-navigation cache that contains only public build assets, never personal API data or credentials, so the recovery route is reachable after reload without claiming background synchronization. Its navigation fallback must exclude OAuth callbacks and every authenticated route/API request. Version activation must preserve the currently usable shell until an explicit update action or a safe completed activation; it cannot strand a pending edit queue or silently discard user state. Implement a locally durable edit queue with account isolation, bounded storage, visible pending state, quota/eviction detection, CSRF/session revalidation before replay, and replay/conflict recovery. Replay runs only in the authenticated page context after it obtains a current CSRF token; the service worker never replays mutations. Never silently clear pending edits on logout or account switch: namespace them by account, keep them inaccessible to another account, surface them on same-account reauthentication, and require a separately confirmed discard. Do not store Canvas credentials in browser storage. Offer an account-scoped export before deletion without making export success a deletion prerequisite. On confirmed deletion, purge that account's IndexedDB queue, pending marker, and app-controlled personal cache, and invalidate stale service-worker replay handles before completion is reported. Test OAuth/API bypass, export, deletion, disconnect, offline reload, app-shell update activation, explicit discard, post-deletion queue purge/replay rejection, and retained planner policy using synthetic data only.
4. Add Playwright coverage for every reachable desktop/mobile screen, control, role/permission state, disabled/recovery state, focus path, reduced-motion behavior, and synthetic visual regression baseline. Produce the dated candidate-current screen-by-screen walkthrough before any deployment trigger; record human screen-reader and nontechnical-pilot checks as external public-pilot evidence, not automated-test claims.

### Phase gate and final commit

- Gate: `npm run test:phase4` passes its focused non-browser checks, then `npm run test:all` runs the one final browser batch, including full browser coverage, offline app-shell reload and update activation, account-isolated pending edits, and explicit-discard recovery; the staged public-history and secret scans plus integrity check are clean; the walkthrough covers the exact candidate; and the final code review records remaining external gates.
- Commit: `Phase 4: accessible student workspace`.
- Only after this gate does the pre-push hook run. If it passes, push all four phase commits once to `main`.

## Red preflight: external gates

These do not block local mocked development. They block staging and live OAuth/deployment:

1. Cloudflare account and free-plan confirmation, stable HTTPS origin, and any D1/Worker creation are owner-authorized external changes.
2. Marymount developer-key approval, exact redirect URI, endpoint scopes, and credential delivery are institution/owner authority. Credentials must enter only through the approved secret broker and remain out of source, tests, logs, and chat.
3. A privacy/support/retention policy, owner confirmation of post-disconnect planner access, export/deletion evidence, human accessibility walkthrough, nontechnical-pilot feedback, live OAuth test, and real Cloudflare free-tier workload evidence are required before any public pilot.

## Definition of done for this plan

The plan is complete when the four phases are accepted in order, each has its local commits and evidence boundary, the final pre-push suite is green, the single final push succeeds, and outstanding Cloudflare/Marymount/public-pilot gates are reported separately rather than claimed complete.
